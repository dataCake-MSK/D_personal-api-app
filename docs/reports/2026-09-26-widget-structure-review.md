# 리포트: 위젯 구조 검토 — 조회/전송 구분, 수동 새로고침, 주기 갱신

- 작성: 2026-09-26
- 상태: 제안 (6장 결정 후 이슈 등록)
- 배경: "API 데이터 위젯과 데이터 전송 위젯은 결국 둘 다 API를 쓰는데 어떻게 구별되나, 합치거나 더 쪼개야 하나, 주기적 수신은 어떻게 하나"

## 1. 요약
- 두 위젯의 진짜 차이는 **"화면에 보여주려고 자동으로 부르는 요청"과 "내가 눌러서 무언가를 시키는 요청"**이다. 기술(HTTP)이 같아도 **되돌릴 수 있는지**가 다르므로 **합치지 않는 것을 권한다.**
- 대신 세 가지를 보완한다: ① **새로고침 버튼**(수동 갱신) ② **자동 갱신 주기**(선택) ③ **이름·설명 정리**(조회/실행이 드러나게).
- 더 쪼개는 것은 권하지 않는다. 표시 형식(텍스트·표·그래프)은 이미 한 위젯 안의 선택지이고, 쪼개면 같은 주소·헤더를 여러 번 입력해야 한다.

## 2. 현재 구분 (2026-09-26 코드 기준)

| | API 데이터 (`http-json`) | 데이터 전송 (`http-action`) |
|---|---|---|
| 목적 | 값을 **가져와 보여줌** | 서버에 **작업을 시킴** |
| 실행 시점 | 위젯이 화면에 뜨면 **자동** | 사용자가 **버튼을 누를 때만** |
| 방식 | GET 고정 | POST·PUT·PATCH·DELETE·GET 선택 |
| 설정 | 값 경로, 표시 형식(텍스트/표/그래프), 축 설정 | 버튼 문구, 보낼 내용(본문), 실행 전 확인 |
| 결과 표시 | 응답에서 꺼낸 값 | 상태 코드만 (본문은 비노출 — 비밀 값 보호) |
| 재요청 | 자동(캐시 30초) | 누를 때마다 1회 |
| 안전장치 | 없어도 됨(읽기만 함) | 실행 전 확인(기본 켬) |
| 공통 | 주소 검사(https), 헤더 + `{{secret:이름}}` 치환, 오류 표시 | 동일 |

- 코드도 공통부(`src/lib/http-request.ts`의 `sendRequest`)를 공유하고, 조회는 `requestJson`, 전송은 `runAction`으로 갈라진다. **이미 중복은 없다.**

## 3. 합칠까, 더 쪼갤까

### 3.1 합치기 (하나의 "API 위젯")
| 장점 | 단점 |
|---|---|
| 위젯 종류가 줄어 처음 고를 때 단순 | **위험**: 한 화면에 "자동 실행"과 "누르면 실행"이 섞이면, 설정 실수로 삭제 API가 자동 호출될 수 있다 |
| 주소·헤더를 한 번만 배우면 됨 | 설정 항목이 합쳐져 폼이 길어지고(표시 형식 + 본문 + 버튼 문구) 무엇이 필요한지 모호해진다 |
| | 응답 본문 노출 정책이 서로 다름(조회는 표시, 전송은 비표시) → 한 위젯에서 상반된 규칙 |

→ **권장하지 않음.** "읽기"와 "쓰기"는 사용자에게도 다른 행동이고, 실수의 대가가 다르다.

### 3.2 더 쪼개기 (표시 형식별 위젯 등)
| 장점 | 단점 |
|---|---|
| 고를 때 결과가 바로 상상됨("그래프 위젯") | 같은 API를 텍스트·표로 함께 보려면 주소·헤더를 두 번 입력 |
| | 형식을 바꾸려면 위젯을 새로 만들어야 함(지금은 수정에서 전환) |
| | 위젯 목록이 길어짐 |

→ **권장하지 않음.** 대신 **추가 화면에서 형식을 먼저 고르게** 해서 체감상 "그래프 위젯을 고른 느낌"을 주는 편이 낫다(5장 B안).

### 3.3 결론
**2종 유지 + 이름·안내 개선.** 기준은 "보여주기 / 시키기"다.

## 4. 수동 새로고침 버튼 (요청사항)
- 지금은 설정을 바꾸면 자동으로 다시 불러오지만(요청 키에 주소·경로가 들어감), **같은 설정에서 최신값을 보고 싶을 때 방법이 없다.** 캐시(30초) 때문에 바로 다시 부르지도 않는다.
- 제안: API 데이터 위젯 카드에 **새로고침** 버튼과 마지막 갱신 시각 표시.
  - 누르면 캐시를 무시하고 즉시 재요청, 진행 중에는 "불러오는 중…" 표시
  - 위젯 카드 조작줄(수정·위로·아래로·삭제)에 함께 두면 일관성 유지
- 구현은 이미 쓰는 TanStack Query의 재요청 기능으로 충분하다(추가 의존성 없음).

## 5. 주기적으로 데이터를 받아와야 할 때

### 5.1 선택지
| 방식 | 동작 | 장점 | 한계 |
|---|---|---|---|
| **A. 주기 갱신 설정** (권장) | 위젯별 간격(예: 30초·1분·5분·수동) 선택 → 화면에 보이는 동안 자동 재요청 | 설정 한 번으로 "살아 있는 대시보드" | **앱이 화면에 있을 때만** 동작 |
| B. 앱을 다시 열 때 갱신 | 앱이 활성화되면 오래된 데이터만 재요청 | 배터리·통신 절약, 자연스러움 | 화면을 계속 보고 있을 때는 갱신 안 됨 |
| C. 백그라운드 갱신 | 앱이 꺼져 있어도 주기 수집 | 알림·기록 가능 | **Expo Go 불가**, 개발 빌드 + OS 제약(수분 단위, 보장 없음) |
| D. 서버가 밀어주기 | 백엔드가 수집·푸시 | 가장 정확·효율 | 백엔드 필요(ADR-0002 재검토) |

### 5.2 권장 조합
1. **A + B를 이번에 구현**: 위젯별 주기 설정(기본 "수동"), 앱을 다시 열 때 오래된 값 갱신.
2. 실시간이 필요한 것은 **WebSocket 위젯(#40)**이 담당한다(주기 호출보다 적합).
3. 앱이 꺼진 동안의 수집·알림은 **백엔드 도입 시점**에 다룬다(알림 D7 결정과 일치).

### 5.3 기술 확인 (공식 문서)
- TanStack Query는 `refetchInterval`로 주기 재요청을 지원하며 이는 캐시 신선도(`staleTime`)와 별개로 동작한다.
- React Native에서는 앱 활성화 감지를 위해 `AppState` 이벤트를 `focusManager`에 연결해야 한다(웹이 아닐 때만). 화면을 벗어난 위젯의 요청을 끊으려면 `useIsFocused`와 `subscribed` 옵션을 쓸 수 있다.
- 기본값으로는 "새 인스턴스 마운트 / 창 포커스 / 네트워크 재연결" 시 오래된 쿼리가 다시 요청된다.

## 6. 사용성·이해도 개선안
| 항목 | 현재 | 제안 |
|---|---|---|
| 위젯 이름 | "API 데이터" / "데이터 전송" | **"API 조회 (보기)"** / **"API 실행 (보내기)"** — 동작이 드러나게 |
| 선택 화면 설명 | 이름만 | 한 줄 설명 추가: "주소에서 값을 가져와 보여줍니다" / "버튼을 눌러 요청을 보냅니다(되돌릴 수 없음)" |
| 표시 형식 | 설정 중간에서 고름 | 추가 시 **형식을 먼저** 고르게(텍스트/표/그래프) → 필요한 입력만 보여줌 |
| 갱신 상태 | 없음 | "○분 전 갱신" + 새로고침 버튼 |
| 위험 안내 | 확인 다이얼로그 | 전송 위젯 설정에 "이 요청은 서버 상태를 바꿀 수 있습니다" 안내 |
