# 요구사항·아키텍처 문서 읽는 법: AC, arc42, C4, ADR

## 핵심 개념

### AC — Acceptance Criteria (수용 기준)
- "이 작업이 **끝났다고 인정하려면 무엇이 참이어야 하는가**"를 체크리스트로 적은 것.
- 좋은 AC는 **확인 가능**하다.
  - ❌ "대시보드가 잘 동작한다"
  - ✅ "위젯 0개일 때 안내 문구가 표시된다"
- AC가 명확할수록 AI에게 맡기기 쉽다 → 명확한 이슈에만 `loop-ready` 라벨을 붙인다.
- 위치: `docs/requirements/SRS.md` 각 항목, GitHub 이슈 본문.

### architecture 폴더 구성
```
docs/architecture/
├─ arc42.md   전체 설명서 (목표·구성요소·공통 규칙·리스크)
├─ c4.md      구조 그림 (L1 시스템 경계, L2 앱 내부)
└─ adr/       결정 기록 (왜 이걸 골랐나)
```

| 문서 | 한 줄 요약 | 비유 |
|---|---|---|
| **arc42.md** | 시스템의 목표, 구성 블록, 공통 규칙, 위험 요소를 정해진 목차로 정리 | 건물 설명서 |
| **c4.md** | 지도처럼 확대 단계별로 그린 구조도. L1 = 앱과 외부의 관계, L2 = 앱 내부 구성 | 건물 도면 |
| **adr/NNNN-*.md** | 되돌리기 어려운 기술 결정 하나당 한 파일. 맥락·결정·대안·결과 | 회의록 |

- arc42 원래 목차는 12개 섹션이지만, 1인 프로젝트라 필요한 6개(1·3·5·8·9·11)만 쓴다.
- C4 원래는 4단계(Context → Container → Component → Code)지만 L1·L2만 쓴다.

### 언제 무엇을 보나
| 상황 | 볼 문서 |
|---|---|
| 오랜만에 돌아와서 전체 그림을 다시 잡고 싶다 | `arc42.md` 1장(목표) → `c4.md` |
| 새 코드를 **어느 폴더에** 둘지 모르겠다 | `arc42.md` 5장(빌딩 블록) |
| 화면·저장소·API가 **어떻게 연결**되는지 보고 싶다 | `c4.md` L2 |
| "왜 Redux 말고 Zustand야?" 같은 **이유**가 궁금하다 | `adr/` 해당 번호 |
| 오류 처리·보안·테스트 **공통 규칙**이 궁금하다 | `arc42.md` 8장 |
| 라이브러리 교체·백엔드 도입 등 **큰 결정**을 하려 한다 | `adr/0000-template.md` 복사해서 새 ADR 작성 |
| 불안한 점(리스크)이 생겼다 | `arc42.md` 11장에 추가 |

### 도식 도구
- 기본은 **Mermaid**: GitHub 웹·모바일에서 바로 그림으로 보인다.
- **PlantUML**: 시퀀스·컴포넌트 다이어그램 표현력이 더 좋다. 단, GitHub 마크다운에서는 코드로만 보이므로 필요할 때만 쓴다.
